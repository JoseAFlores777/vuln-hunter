Panel vivo de auditoría

Un panel administrativo estático (React por CDN, sin build ni instalación) que lee el ledger y un nuevo registro de actividad, y se actualiza solo para que el usuario vea aparecer las vulnerabilidades y cómo se van mitigando — en tiempo real.

§ 01Objetivo y arquitectura

Qué construye y con qué forma.

Objetivo. Un panel React vía CDN que lee .vuln-hunter/ledger.json + un nuevo .vuln-hunter/activity.jsonl y auto-refresca, para que el usuario observe en vivo los hallazgos y su mitigación, servido con python3 -m http.server.

Arquitectura. Contrato de dos archivos — el ledger sigue siendo la única verdad de estado (findings, statuses, mitigación); un nuevo activity.jsonl append-only lleva el timeline de eventos. Un helper compartido scripts/activity.py hace append; cada comando de etapa lo llama en sus bordes. Un solo panel/index.html (React 18 + Babel standalone por CDN, cero build) hace polling de ambos archivos cada 2s y renderiza una página única con filas de finding expandibles.

Límite de liveness. Los subagentes Task son opacos: el hilo principal no recibe nada hasta que retornan. Por eso "vivo" es por-etapa y por-finding, no token a token. Documentado en docs/adr/0001-panel-liveness-architecture.md.

Tech stack. Python 3 stdlib (activity.py, unittest, http.server), React 18 UMD + @babel/standalone por unpkg, CSS plano con la paleta del kit.

§ 04Contrato de eventos

El split estado/eventos y los únicos tipos válidos.

El ledger guarda la verdad de estado; activity.jsonl es solo el timeline. El panel deriva el estado de cada agente (idle/running/done) del último stage:* de su etapa, y lee la mitigación directo del ledger.

# una línea JSON por evento; tipos válidos:
run:start      {scope}
run:done       {}
stage:start    {stage, agent?}
stage:end      {stage, agent?, summary?}
finding:new    {id, title, source}
deploy:blocked {reason}
El estado de los agentes y los cambios de status de los findings no se duplican en eventos: se derivan del ledger. Así activity.jsonl no compite con el contrato que ya consumen los 7 agentes.

§ 05Tareas

8 tareas TDD, pasos bite-sized. El detalle completo (con todo el código) vive en el .md; aquí el mapa.

Task 1 — Logger de eventos (scripts/activity.py)

TDD con unittest: parseo k=v, append JSONL con ts+type, validación de tipo, creación de dir. Núcleo:

def append_event(event_type, fields, path):
    if event_type not in EVENT_TYPES:
        return 2
    rec = {"ts": datetime.now().isoformat(timespec="seconds"), "type": event_type}
    rec.update(fields)
    os.makedirs(os.path.dirname(path) or ".", exist_ok=True)
    with open(path, "a") as fh:
        fh.write(json.dumps(rec, ensure_ascii=False) + "\n")
    return 0

Task 2 — Fixtures de verificación

Un ledger mid-audit (1 cerrada, 1 corregida-pendiente, 1 P0 KEV) + un activity.jsonl que se detiene en mitad de FIX (un stage:start sin stage:end) para que el panel muestre appsec-fixer como running.

Task 3 — El panel (panel/index.html)

App React CDN de un archivo. Componentes: SummaryCards, PipelineBar, AgentRoster, FindingsTable (filas expandibles), ActivityTimeline. Polling 2s con cache-busting; deriva estado de agentes; ensambla la explicación de cada finding desde los sub-objetos del ledger. Verificación visual contra los fixtures con observaciones explícitas (pipeline FIX ● running, roster appsec-fixer running, etc.).

Task 4 — Comando lanzador (commands/panel.md)

(python3 -m http.server ${ARGUMENTS:-8765} --directory .vuln-hunter &) ; \
  sleep 1 ; open "http://localhost:${ARGUMENTS:-8765}/index.html"

Task 5 — Instrumentar orquestador (hunt.md + detect.md)

Añade Bash(python3:*) a allowed-tools y una sección que emite eventos en los bordes de cada etapa, run:start al inicio y run:done al final.

Task 6 — Instrumentar comandos de etapa solos

Para que el timeline funcione también corriendo etapas sueltas. Tabla (file → stage → agent) + plantilla exacta + ejemplo concreto para scan.md.

Task 7 — Documentar (README.md)

Entrada para /vuln-hunter:panel y una frase de arquitectura apuntando al ADR.

Task 8 — Verificación end-to-end

Suite completa de tests + simular una auditoría viva (escribir eventos reales con activity.py y ver el panel actualizar en ~2s sin recargar) + chequeo de estado vacío.

§ 06Verificación

Evidencia, no afirmaciones (CLAUDE.md §9: verificación honesta).

  • Unit: python3 tests/test_activity.py -v — 6 tests del logger.
  • Contrato: python3 tests/test_panel_contract.py -v — forma de fixtures + el HTML referencia ledger.json, activity.jsonl, React/Babel CDN, setInterval y los 4 componentes.
  • Visual: servir fixtures con http.server y observar pipeline/roster/tabla/timeline (lista de observaciones esperadas en el .md).
  • End-to-end: append de eventos reales → el panel cambia en ~2s sin recargar.
  • Estado vacío: sin ledger → mensaje guía, no crash.
El JS en navegador no se unit-testea (sin Node, por diseño "sin instalar nada"). Esa cobertura es verificación visual/manual con observaciones explícitas — declarada como tal, no fingida.
